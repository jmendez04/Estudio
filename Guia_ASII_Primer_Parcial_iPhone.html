🧩 3. Serie II — desarrolla sin escribir una biblia

En cada tema tienes una respuesta compacta que sí puedes desarrollar en examen.

1) Diseño arquitectónico en Ingeniería de Software

Representa la estructura de datos y componentes necesarios para construir el sistema. Considera el estilo arquitectónico, la estructura y propiedades de los componentes y sus interrelaciones.

  • Importancia: facilita comunicación, resalta decisiones tempranas y crea un modelo manejable del sistema.
  • Proceso: diseño de datos → representación de la estructura → análisis de alternativas → elaboración de la arquitectura.
2) UML

UML es un lenguaje de modelado que ayuda a representar visualmente la estructura y comportamiento de un sistema.

Para este parcial, relaciona UML principalmente con diagramas que ayudan a documentar y comprender el sistema; en tus preguntas aparece especialmente el diagrama de componentes UML, que muestra componentes, interfaces, dependencias y estructura modular.

3) Metodología YOURDON

En tus preguntas se divide en tres aspectos:

  • Ambiental: entradas y salidas del sistema con su entorno; usa diagrama de contexto.
  • Comportamiento: cómo el sistema procesa entradas para producir salidas; usa DFD y transición de estados.
  • Información: persistencia de datos utilizados por los procesos; usa diagrama entidad–relación.
4) Modelado de procesos

Modelo: representación de una realidad que ayuda a organizar y documentar información de un sistema.

Modelar: desarrollar una descripción lo más exacta posible del sistema y las actividades que se realizan en él.

Diagramar: establecer una representación visual de procesos y subprocesos.

5) Análisis de sistemas

En tus preguntas aparece como el análisis de las reglas del negocio y de las necesidades de soporte de información. Primero se entiende el problema; después se diseña la solución.

Conecta bien esta idea con espacio del problema (formulación + análisis) y espacio de la solución (búsqueda + selección + diseño + implementación).

🛠️ 4. Serie III — SRP sin pánico

Lo que debes ver: una clase hace demasiadas cosas y tiene varias razones para cambiar.

EXAMENSOLID · S
class Pedido { calcularTotal() { ... } guardarEnBD() { ... } generarFacturaPDF() { ... } enviarCorreo() { ... } }
Qué dices: viola el Principio de Responsabilidad Única porque mezcla lógica del pedido, persistencia, generación de documentos y notificación; son responsabilidades con razones de cambio distintas.

Una separación razonable

class Pedido { calcularTotal() { ... } } class PedidoRepository { guardar(pedido) { ... } } class FacturaPDF { generar(pedido) { ... } } class Notificador { enviarCorreo(pedido) { ... } }
¿Cuál es la señal más clara de SRP?
